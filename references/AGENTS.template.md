## Project workflow: Main / Chief / Worker / Reviewer

- Project: `{{PROJECT_NAME}}`
- Initialized at: `{{INITIALIZED_AT}}`
- Runtime state: `Workflow/STATE.json`
- Durable knowledge: `MEMORY.md`
- Semantic plan: `Workflow/PLAN.md`
- Runtime handoff: `Workflow/MAIN_BRIEF.md`

### Authority boundary

- Main/Orchestrator is the current main conversation and Runtime center. Main owns dispatch, runtime order and concurrency, retries, evidence collection, state updates, and bounded adaptation inside the accepted plan.
- Chief is a persistent high-intelligence planning and decision subagent. Chief owns Initial Global Planning and plan-level decisions, not routine orchestration, progress noise, or ordinary implementation.
- Worker implements and verifies one bounded task. Worker cannot redefine the plan, acceptance criteria, or architecture and cannot self-certify `PASS`.
- Worker returns ambiguity, missing information, scope expansion, repository conflict, and project-rule conflict as `BLOCKED` with evidence to Main. Worker never directly invokes, messages, or escalates to Chief.
- Reviewer independently checks the original task, actual diff, and evidence. Reviewer does not edit implementation files, has no architecture decision authority, and never directly invokes or messages Chief.
- Expert Worker is a temporary, fresh, isolated Chief-class coding subagent. It is not Chief, cannot approve its own work, returns runtime issues to Main, and must return to the same Reviewer policy after implementation.
- Main is the only Runtime routing center. Main decides whether a `BLOCKED` issue is solvable inside the accepted plan or requires Chief.

Use the rule: “Main owns adaptation inside an accepted plan. Chief owns interpretation and changes to the plan itself.” Changes to the user goal, architecture, public/interface semantics, ownership, global acceptance criteria, task objective meaning, semantic dependencies, or confirmed constraints require Chief.

### Workflow protocol

1. For a large initial prompt, Main prepares context and invokes persistent Chief for Initial Global Planning.
2. Chief writes `Workflow/PLAN.md`, `Workflow/MAIN_BRIEF.md`, initial task packets, and high-value Memory candidates. Chief records semantic dependencies only; it does not plan runtime concurrency.
3. Main validates the planning artifacts, selects runtime order and effective concurrency, and dispatches Workers and Reviewers.
4. Worker writes `Workflow/results/<task-id>.md`; Reviewer writes `Workflow/reviews/<task-id>-r<N>.md` or uses a bundle under `Workflow/review-bundles/<task-id>/<attempt>/`.
5. Only a formal Reviewer `FAIL` increments `worker_failures`. After FAIL #1, Main sends a concise escalation packet to Chief and receives a Decision Delta.
6. On FAIL #2, Main dispatches a fresh isolated Expert Worker directly unless the Reviewer explicitly provides plan-level evidence; Expert Worker returns to the same Reviewer policy, and its FAIL goes to Chief through Main.
7. `PASS` closes a task only after acceptance criteria, evidence, state, and durable Memory candidates are handled. `BLOCKED` returns to Main/Chief as appropriate.

### Same-session interruption recovery

- Network/provider errors, rate limits, transient timeouts, and context or thinking-token limits are recoverable interruptions first. Preserve the original Subagent/session and send `继续` to that same session with the last checkpoint and remaining acceptance criteria.
- Record `subagent_interrupted`, `subagent_resume_requested`, and `subagent_resumed` in `Workflow/events.jsonl`; update the role heartbeat before and after continuation. Do not count a transient interruption as Reviewer `FAIL` or `worker_failures`.
- Do not open a replacement Subagent unless the original session is explicitly unavailable/expired or bounded continuation attempts fail with evidence. Preserve the original record and keep the same role model/depth and Reviewer policy unless a documented Chief/user decision authorizes change.

### Concurrency quality gate

- Worker and Reviewer subagents may run concurrently, but Main decides effective parallelism. `max_worker_concurrency` is a hard Worker ceiling, not a promise to use it.
- A requested Worker pair with overlapping writable scope in a shared worktree is a hard block. Isolated worktrees are required to override that guard.
- Parallelize only with separate objectives, disjoint writable scopes, satisfied semantic dependencies, isolated tests/resources, stable review evidence, and acceptable aggregate risk.
- Default to serial execution when isolation or quality impact is unclear, or for security, data loss, destructive operations, shared architecture, public release, or tightly coupled integration work.
- Main records Worker concurrency, Reviewer concurrency, isolation boundaries, dependency assumptions, test isolation, and the quality rationale in the task packet. Programs may emit `SAFE`, `WARNING`, or `BLOCKED` guardrail signals but do not replace Main with an automatic scheduler.

### Artifact layout

- `Workflow/PLAN.md` — semantic plan and dependency graph; never a runtime concurrency plan
- `Workflow/MAIN_BRIEF.md` — concise Chief-to-Main Runtime Handoff
- `Workflow/STATE.json` — current operational state, attempts, failures, jobs, and paths
- `Workflow/events.jsonl` — append-only runtime events; routine events do not go into `MEMORY.md`
- `Workflow/tasks/` — task packets
- `Workflow/results/` — Worker results
- `Workflow/reviews/` — Reviewer reports
- `Workflow/review-bundles/<task-id>/<attempt>/` — immutable bundle-first Reviewer inputs
- `Workflow/decisions/` — Chief Decision Deltas and escalations
- `Workflow/config.json` — declared role models, Worker concurrency ceiling, and per-role thinking depths
- `Workflow/watchdog.json` — visible Watchdog settings and last-check projection
- `Workflow/heartbeats.json` — latest visible heartbeat for Main and delegated roles
- `Workflow/watchdog-alerts.jsonl` — append-only suspected-stall reports for Main

### Runtime and evidence rules

- Read `Workflow/config.json`, `Workflow/STATE.json`, and the relevant plan/brief before dispatch.
- Use `Workflow/events.jsonl` for `task_started`, dispatch, completion, review, repair, interruption, continuation, and state events. `MEMORY.md` stores durable knowledge only; Worker/Reviewer submit Memory candidates and Main gates their merge.
- Start the visible Watchdog before dispatching roles; it checks every 600 seconds by default and reports stale heartbeat/runtime evidence to Main as a suspected network/provider/unresponsive-agent stall. Main decides the response; Watchdog never restarts agents, changes models, or bypasses Main.
- `exit_code == 0` with `executed_tests == 0` is `INVALID_TEST_EXECUTION`, never a valid test `PASS`.
- Reviewer `FAIL` reports must include Findings, Evidence, Likely Root Cause, Recommended Solution, Affected Scope, Regression Risks, and Confidence. A recommendation is not repair or architecture authorization.
- Review Bundles are starting context, not an information boundary. Reviewer may inspect additional files and run targeted checks. Changed input hashes or unstable evidence require a new bundle/review attempt.

### Safety and compatibility

- Preserve project-specific content outside managed markers. Before initializing an unmarked `AGENTS.md` or `MEMORY.md`, ask for merge, explicit overwrite, or cancel; never infer overwrite permission.
- Keep canonical artifacts in visible `Workflow/`. Migrate legacy `.workflow/` only with explicit approval and preserve the legacy directory as a backup.
- Never create `.workflow/` or another hidden workflow directory for a new project.
- v1.3 configuration and history remain readable; missing v1.4 artifacts are created only when absent. Do not delete history or overwrite unmanaged files.
- Never store secrets, tokens, private keys, passwords, or sensitive personal data in project Markdown or Workflow artifacts.
