## Project workflow: Chief / Worker / Reviewer

This managed section is generated by `chef-worker-reviewer-workflow`.

- Workflow version: `1.3`
- Project: `{{PROJECT_NAME}}`
- Initialized at: `{{INITIALIZED_AT}}`
- Durable state: `MEMORY.md`
- Detailed artifacts: `Workflow/`

### Role contract

#### Chief / Chef (current main conversation)

- Treat the current main conversation model as Chef; do not spawn a separate Chef subagent for routine planning or arbitration.
- Define the objective, scope, exclusions, acceptance criteria, dependencies, risks, and verification commands.
- Create task packets, route bounded work, maintain workflow state, and make recorded decisions.
- Resolve Worker–Reviewer conflicts with evidence.
- Stop scope expansion, repeated failure, and architecture or safety conflicts.
- Do not treat a Worker summary as proof of completion.

#### Worker

- Read the task packet and project instructions before editing.
- Implement only the assigned scope and keep the diff minimal and coherent.
- Run the required tests and write a result with changed files and evidence.
- Stop and report ambiguity, missing authority, or scope conflict.
- Do not change the Chief's plan or self-certify a task as passed.

#### Reviewer

- Use fresh context where possible.
- Inspect the original task, actual diff, and Worker evidence.
- Check every acceptance criterion and reproduce important claims.
- Return `PASS`, `FAIL`, or `BLOCKED`, with severity, location, evidence, and required action for each finding.
- Do not edit implementation files or silently fix what is being reviewed.

### Workflow protocol

1. Chief writes `Workflow/tasks/<task-id>.md`.
2. Worker implements and writes `Workflow/results/<task-id>.md`.
3. Reviewer writes `Workflow/reviews/<task-id>-r<N>.md`.
4. `PASS` closes the task; `FAIL` creates a bounded repair; `BLOCKED` returns to Chief.
5. Escalate after three repairs with the same root cause, unresolved role conflict, scope expansion, or critical risk.

### Concurrency quality gate

- Worker and Reviewer subagents may run concurrently, but Chef decides the effective parallelism for each task; `max_worker_concurrency` is a hard Worker ceiling, not a promise to use it.
- Parallelize only with separate objectives, disjoint writable scopes, no unmaterialized dependencies, isolated tests and resources, independent Reviewer evidence, and acceptable aggregate risk.
- Default to serial execution when isolation or quality impact is unclear, or when work involves security, data loss, destructive actions, shared architecture, public release, or tightly coupled integration behavior.
- Chef records Worker concurrency, Reviewer concurrency, isolation boundaries, dependency assumptions, test isolation, and the quality rationale in the task packet. Conflicting parallel results return to a bounded serial phase.

### Evidence rules

- Review the actual diff and run relevant checks; do not rely on prose alone.
- Distinguish verified facts, inference, and suggestions.
- An inferential finding must be verified before repair.
- Never weaken acceptance criteria to force a pass without a recorded Chief decision.

### Artifact layout

- `Workflow/tasks/` — task packets
- `Workflow/results/` — Worker results
- `Workflow/reviews/` — Reviewer reports
- `Workflow/decisions/` — Chief decisions and escalations
- `Workflow/config.json` — selected models, concurrency limit, and thinking depth
- `MEMORY.md` — concise state, ledger, decisions, and work log

### Runtime configuration

- Read `Workflow/config.json` before dispatching any role.
- The configured Chef model is the declared identity of the current main conversation; Worker and Reviewer are the delegated roles.
- At the beginning of each task, remind the user of this Chef/Worker/Reviewer relationship.
- If the harness exposes an actual current main-conversation model and it differs from the configured Chef model, pause and ask for a switch or explicit reconfiguration.
- Respect the configured Worker concurrency limit; do not exceed it even when tasks appear independent.
- Do not treat concurrency as a quality shortcut: Chef must judge whether Worker or Reviewer parallelism preserves quality, and must synthesize concurrent Reviewer verdicts before repair or completion.
- Use the configured thinking depth unless Chief records an explicit reconfiguration decision.
- Do not replace a configured model with a silent fallback. If a model or thinking depth is unavailable, stop and report the configuration problem.

### Safety

- Preserve project-specific instructions outside the managed markers.
- Before initializing in a project with an unmarked `AGENTS.md` or `MEMORY.md`, ask the user to choose merge, explicit overwrite, or cancel.
- Keep the canonical workflow artifacts in visible `Workflow/`; do not create hidden `.workflow/` for new work. Migrate legacy `.workflow/` only with explicit approval and preserve the legacy directory as a backup.
- Never treat an ambiguous acknowledgement as permission to overwrite project files.
- Do not store secrets or sensitive personal data in project Markdown or workflow artifacts.
- If an existing project rule conflicts with this section, stop and ask Chief or the user.
